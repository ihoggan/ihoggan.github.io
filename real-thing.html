Is it the real thing?

While updating my desktop today, I found two copies of the same app. One came straight from the company that makes it. The other was a look-alike, packaged by a volunteer I'd never heard of, under the same name. Nothing bad had happened, but I hadn't chosen it on purpose and couldn't remember installing it. This page is the six checks I used to find out, so you can run them on your own machine. Every one of them only reads. Nothing here changes anything.

Before you start

A name is not a maker

On Ubuntu, programs usually arrive in one of four ways: apt (Ubuntu's own package manager), snap, Flatpak, or a file you downloaded yourself, such as an AppImage. Anyone can publish under almost any name in some of these places. So "it's called Firefox" or "it's called the thing I use at work" tells you nothing about who built it, or who can change it later.

That matters, because installing software is handing over trust. When you install with sudo apt, the package's own setup scripts run as root, the all-powerful account. Whoever controls that package controls what runs next time it updates.

Predict first

Think of one app you use every day. Do you know which of those four routes it came by, and who publishes it? Write your guess down. You'll check it in a minute.

You'll need a terminal. If it's new to you, Meet the terminal starts from nothing. In the commands below, swap firefox for whatever app you're checking.

Check 1

Which copy runs when you type its name?

type -a firefox

This lists every program with that name that your shell can find, in the order it looks for them. The first one listed is the one that runs.

On one Ubuntu machine, for example:

$ type -a firefox
firefox is /snap/bin/firefox
firefox is /usr/bin/firefox
  • Anything under /snap/bin is a snap.
  • Anything under /usr/bin usually came from apt.
  • Anything under your home folder, such as ~/.local/bin, was put there by you, or by something you ran.
Don't be fooled by this one

On modern Ubuntu, /bin is just another name for /usr/bin. If you see the same program listed under both, it's one file, not two. I nearly counted mine twice.

Check

You know which path runs when you type the app's name, and whether more than one copy exists.

Check 2

Which package owns that file?

For anything in /usr/bin, ask apt's database which package put it there:

dpkg -S "$(readlink -f "$(command -v firefox)")"

Read it from the inside out: command -v finds the program, readlink -f follows any shortcuts to the real file, and dpkg -S names the package that owns it. If it says no path found, apt didn't install that file. Something else did, and that's worth knowing.

For the other routes:

snap list                                         # every snap, with its publisher
flatpak list --app --columns=application,origin   # if you use Flatpak at all
Check

You can name the package, snap or Flatpak that each copy belongs to. Compare it with the guess you wrote down.

Check 3

Where does apt get it from?

apt-cache policy firefox

Look at the web addresses in the output. They're where updates will come from:

$ apt-cache policy claude-desktop
claude-desktop:
  Installed: 4.4212.0
  Candidate: 4.16336.0
  Version table:
     4.16336.0 500
        500 https://downloads.claude.ai/claude-desktop/apt/stable stable/main amd64 Packages
 *** 4.4212.0 500
        100 /var/lib/dpkg/status

That's the AI desktop app I use, coming from its maker's own domain. Installed is what you have; Candidate is what apt would upgrade you to. As a rough guide to the addresses:

You seeIt means
archive.ubuntu.com, security.ubuntu.comUbuntu itself.
The maker's own domainThe vendor's official repository. Check it against their install page.
ppa.launchpadcontent.netA personal package archive: someone's own packages, hosted by Ubuntu. Could be the maker, could be anyone.
Anything else, e.g. a github.io addressOften a community rebuild. Not necessarily bad, but not the maker.
Check

You know which web address your app updates from, and whether it belongs to the people who make it.

Check 4

Who signed it?

An address can be faked or mistyped. What apt actually trusts is a signing key. Each source on your system names the key that its packages must be signed with:

ls /etc/apt/sources.list.d/
cat /etc/apt/sources.list.d/ubuntu.sources
$ cat /etc/apt/sources.list.d/ubuntu.sources
Types: deb
URIs: http://archive.ubuntu.com/ubuntu/
Suites: noble noble-updates noble-backports
Components: main universe restricted multiverse
Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg

The Signed-By line points at the key file. Ask it who it belongs to:

$ gpg --show-keys /usr/share/keyrings/ubuntu-archive-keyring.gpg
pub   rsa4096 2012-05-11 [SC]
      790B C727 7767 219C 42C8  6F93 3B4F E6AC C0B2 1F32
uid   Ubuntu Archive Automatic Signing Key (2012) <ftpmaster@ubuntu.com>

That long string is the key's fingerprint. The name after uid is just a label anyone could type. The fingerprint is the part that can't be faked. For a vendor's own source, compare it with the fingerprint printed on the vendor's install page. If they match, the packages really are signed by them.

Older guides use a single file, /etc/apt/sources.list, or a line format like deb [signed-by=...] https://.... It's the same idea in a different layout: look for signed-by.

Lesson

A source with no Signed-By at all trusts every key on your system. That's the one to look at hardest.

Check 5

Who published that snap?

snap info firefox | grep -E '^(name|publisher|store-url)'

The publisher line is the account that uploaded it. The Snap Store adds two marks you'll see by some names:

  • A tick (✓): a verified publisher. The Snap Store has checked that this account is the organisation it says it is.
  • A star: a Star Developer, an individual the store recognises as an active, responsible member of the community. In a plain terminal, mine showed as an asterisk after the name.

Neither mark says the snap is the official version of the app it's named after. My look-alike had a star. Its publisher was a real, active volunteer, and the store page said plainly that it wasn't the official app. A star tells you about the packager, not about the brand.

Think about it

If the company that makes an app doesn't publish a snap of it, who decides what goes into a snap with that app's name?

The answer

Whoever packaged it. They choose which version goes in, when it updates, and what else comes with it. That can be perfectly fine, but it's a person you're trusting, so it should be a choice you made on purpose.

The store page, at snapcraft.io/ followed by the snap's name, often says in its description whether the snap is official. Read it.

Check 6

Hunt for duplicates

Now look for every copy, from every route, in one go. Replace firefox with your app's name:

app=firefox
dpkg -l | grep -i "$app" || echo "no apt package"
snap list 2>/dev/null | grep -i "$app" || echo "no snap"
flatpak list 2>/dev/null | grep -i "$app" || echo "no flatpak"
find ~ -maxdepth 3 -iname "*$app*.AppImage" 2>/dev/null

This is how I found mine. The official app came from apt, as I expected. The look-alike turned up in the snap list line.

Check

You've found every copy of your app, and you know which route each one came by and who publishes it.

Then what?

Deciding what stays

Finding a copy you didn't expect isn't an emergency. Most community packagers are generous people filling a gap. The question is simply: did you choose this?

  1. Work out what you actually use. Check 1 tells you which copy runs. The others may be sitting unused.
  2. Find the maker's own install page, and see which route they recommend for Ubuntu.
  3. Remove the copy you didn't choose, and only that one. Run the checks again before you remove anything, and again afterwards. For a snap, the command is sudo snap remove followed by its name.

I'm sorting mine out the same way: read-only checks first, then a decision, then the change. That habit has its own page: Look before you leap.

What I'd want you to take away

A name isn't a maker

Anyone can package an app under its name. Check the publisher, not the label.

The key is the trust

For apt, the signing key's fingerprint is what proves who built a package. The web address is just where it's kept.

One of each, on purpose

Two copies of an app means two people you're trusting. Keep the one you chose.
