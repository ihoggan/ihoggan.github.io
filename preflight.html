Look before you leap

Pilots don't start an engine and then check the fuel. Every change I make on my machines works the same way: read-only checks first, then a GO or a NO-GO, and only then the command that changes something. This page shows the habit, a real time it saved me, and a small guard you can build that refuses to push your private words to a public repository.

Part 1

Two kinds of command

Every command you type in a terminal does one of two things. It looks, or it changes. Looking is always safe: run it as often as you like. Changing is where mistakes live, and some changes can't be taken back.

Looks (safe any time)Changes (check first)
ls, cat, pwd, df -hmv, cp, rm, mkdir
git status, git log, git diffgit commit, git reset, git push
apt-cache policy, dpkg -lsudo apt install, sudo apt remove
systemctl status, lsusb, pgrepsystemctl enable, sudo tee, chmod

A handy rule of thumb: sudo almost always means a change. So does anything with > in it, which writes to a file.

Predict first

Which column does git fetch go in? It downloads, but does it change your files?

The answer

It's a looker, as far as your work is concerned. It updates git's record of what's on the server, but never touches your files or your branch. That's why it's in my pre-flight checks below.

Part 2

Write down what you want before you look

A pre-flight is a short list of looking commands, each with the answer you expect written next to it. Before I copy a change into my website's folder, it's this:

cd ~/code/my-site
git status --short                    # want: empty (nothing half-done)
git branch --show-current             # want: main
git fetch -q && git log -1 --oneline origin/main   # want: the commit I expect
git log -1 --oneline                  # want: the same commit
ls -l ~/Downloads/new-page.patch      # want: the file, about the size I expect

Writing the "want" first matters. If you look first, it's very easy to decide that whatever you see is fine. If you've written down what fine looks like, a surprise jumps out.

Then, before giving a GO, I ask three questions:

Am I where I think?Right machine, right folder, right branch. The prompt tells you the first two; git branch tells you the third.
Is it how I think?Nothing half-finished, nothing newer on the server, the file I need is actually there.
Can I undo it?If not, slow down even more. A push to a public repository is the obvious one: once it's out, assume it's been copied.

Part 3

The day it said NO-GO

Earlier today I was adding a new page to this site. The checks came back like this (trimmed, with the file name simplified):

$ git status --short
$ git branch --show-current
main
$ git log -1 --oneline
9db8a87 Add case study: Meet Gus
$ ls -l ~/Downloads/new-page.patch
ls: cannot access '/home/me/Downloads/new-page.patch': No such file or directory

Everything was where it should be, except the one file I needed. I'd clicked past it without downloading it. Without the check, the next commands would have failed halfway through a change, with part of it done and part not, and I'd have been untangling it instead of publishing.

Instead it was a NO-GO. I downloaded the file, ran the checks again, got all the answers I'd written down, and gave it a GO.

Lesson

A NO-GO isn't a failure. It's the check doing its job, at the moment it's cheapest to fix.

Part 4

The change you can't take back

Most mistakes on your own machine can be undone. A push to a public repository can't, not really: within minutes, anything public can be copied, cached or scraped. So the push gets the strictest check of all. I run my own tool, git preflight, before every one. Its last report looked like this:

Repository
  PASS  On branch 'main'
GitHub access
  PASS  GitHub accepts this machine's SSH key
Working tree
  PASS  No uncommitted changes to tracked files
Sync with remote
  PASS  Not behind origin/main
  PASS  1 commit(s) ready to push
Content of the 1 outgoing commit(s)
  PASS  No passwords, keys or tokens spotted
  PASS  No watchlist words (20 checked)
  PASS  Commits use a noreply email address
Visibility
  WARN  This repo is PUBLIC — anyone can read what you push.

CLEAR TO PUSH — 1 warning(s).

The line I care about most is "No watchlist words". I keep a private list of words that must never appear in anything public: places, names and accounts that are nobody else's business. The list lives on my machine, outside every repository, so it can never be pushed itself. Before anything goes out, every outgoing change is checked against it.

You can build the core of that yourself, right now, in about twenty lines.

Part 5

Build your own watchlist guard

Git can run a script of yours at certain moments. These are called hooks. A pre-push hook runs just before a push. If it ends with an error, the push doesn't happen. That's exactly what we want.

1. Your private list

One word or phrase per line. Use your own, but for practice, start with these made-up ones:

mkdir -p ~/.config/watchlist
printf 'Acacia Avenue\nFluffykins\n' > ~/.config/watchlist/words
chmod 600 ~/.config/watchlist/words     # readable by you only

It lives in your home folder's .config, not inside any project, so no git add can ever pick it up. Later, add the real things you never want public, one per line: your road, your town, your pets' names, your employer.

2. A practice repository

Don't test a guard on something precious. Make a throwaway pair: a "server" folder and a working folder that pushes to it.

mkdir -p ~/practice && cd ~/practice
git init -q --bare practice-remote.git
git init -q -b main practice && cd practice
git remote add origin ../practice-remote.git

3. The hook

Save this as .git/hooks/pre-push inside the practice folder. A text editor is fine: nano .git/hooks/pre-push, paste it in, then Ctrl + O to save and Ctrl + X to leave.

#!/usr/bin/env bash
# pre-push: refuse to push if anything outgoing mentions a word on your private watchlist.
# The list lives outside every repo, one word or phrase per line.
list="$HOME/.config/watchlist/words"
if [ ! -r "$list" ]; then
  echo "pre-push: no watchlist at $list, so refusing to push." >&2
  exit 1
fi
zero=0000000000000000000000000000000000000000
found=0
while read -r local_ref local_sha remote_ref remote_sha; do
  [ "$local_sha" = "$zero" ] && continue                 # deleting a branch: nothing to check
  if [ "$remote_sha" = "$zero" ]; then
    range=("$local_sha" --not --remotes)                  # new branch: everything not already on the remote
  else
    range=("$remote_sha..$local_sha")                     # existing branch: just the new commits
  fi
  hits=$(git log -p --format='commit %h %s%n%b' "${range[@]}" \
         | grep -i -n -F -f <(grep -v '^[[:space:]]*$' "$list"))
  if [ -n "$hits" ]; then
    echo "pre-push: watchlist words found in what you're about to push:" >&2
    echo "$hits" >&2
    found=1
  fi
done
if [ "$found" -ne 0 ]; then
  echo "pre-push: NO-GO. Nothing was pushed." >&2
  exit 1
fi
echo "pre-push: watchlist clear."

Then make it runnable:

chmod +x .git/hooks/pre-push
How it works, line by line

Git hands the hook one line per branch being pushed: what you're sending and what the server already has. The hook asks git log -p for every outgoing commit, including its message and every line it changes, and runs it through grep with your list. -i ignores capitals, -F treats your words as plain text rather than patterns, and the inner grep -v drops blank lines from your list. (A blank line would match everything.) If no list is found at all, it refuses: a guard that silently does nothing is worse than none.

4. Test it: a clean push, then a dirty one

Predict first

The first commit below is harmless. The second mentions a made-up pet that's on the list. What will each push print?

git config user.name "You"; git config user.email "you@example.com"   # practice repo only
echo "Hello world" > notes.txt
git add notes.txt && git commit -qm "First notes"
git push origin main

echo "Our cat is called Fluffykins" >> notes.txt
git commit -qam "More notes"
git push origin main
$ git push origin main
pre-push: watchlist clear.
…
$ git push origin main
pre-push: watchlist words found in what you're about to push:
10:+Our cat is called Fluffykins
pre-push: NO-GO. Nothing was pushed.
error: failed to push some refs to '../practice-remote.git'

The + shows it's a line being added. The commit never left your machine.

5. Fix it and go again

git reset HEAD~1          # undo the last commit, keep the file as it is
nano notes.txt            # take the name out
git commit -qam "More notes"
git push origin main      # want: watchlist clear

git reset HEAD~1 is safe here because that commit never left your machine, which is exactly the situation the hook leaves you in. Don't use it to undo commits that are already on the server.

Check

Your hook let a clean push through, stopped one with a watchlist word, and let the fixed version through.

6. Put it on your real projects

Hooks live inside each project's .git folder, and they aren't copied when you clone. So copy it into each project you push from:

cp ~/practice/practice/.git/hooks/pre-push ~/code/my-site/.git/hooks/
chmod +x ~/code/my-site/.git/hooks/pre-push
Know its limits

It's a seatbelt, not a lock. git push --no-verify skips hooks completely, and it only checks text, not words inside pictures or PDFs. It can't catch what isn't on your list either, so keep the list up to date.

It also only guards what you push from now on. If something private was pushed in the past, it's still in the history. Removing it properly is a bigger job.

Part 6

Make it a habit

The hook is the last line of defence. The habit is the first. Next time you're about to type a command that changes something, stop and ask:

  1. What do I expect to be true right now? Write it down.
  2. Which looking commands would prove it?
  3. Do the answers match? GO. If they don't, NO-GO: fix that first, then check again.

It feels slow for about a week. Then it feels like the only sane way to work.

What I'd want you to take away

Look, decide, act

Read-only checks first, the answer you expect written beside each, then GO or NO-GO.

NO-GO is a win

It caught the problem at the moment it was cheapest to fix, before anything had changed.

Guard the one-way door

A push to a public repository can't be taken back. Put a check in front of it that knows your private words.
