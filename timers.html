A reminder that never forgets

One app I use every day doesn't update itself on Linux, and I kept forgetting to check. So now my desktop checks for me, every Tuesday at nine in the evening, and pops up a note if a new version is waiting. It never installs anything itself. That stays my decision. This page builds the same thing for an app of yours: your first systemd timer, one small piece at a time, with a test at every step.

Before you start

Why it only tells you

It would be easy to make the computer install updates by itself. I deliberately don't. An install is a change, and every change on my machines gets read-only checks and a GO first (Look before you leap explains why). A job that installs things on its own at 9pm skips all that. So this timer does the looking, and leaves the doing to me.

You'll need:

  • Ubuntu with a desktop, and a terminal. If it's new, start with Meet the terminal.
  • The apt package name of an app you care about. Is it the real thing? shows how to find it. Below I use git; swap in yours. (Snaps update themselves, so this is for apt packages.)

Nothing here needs sudo. It all runs as you, from files in your own home folder.

Step 1

Where does "a new version is waiting" come from?

Ubuntu already refreshes its list of available versions once a day, with a timer of its own. Have a look at it:

systemctl list-timers apt-daily.timer

Then ask apt about your app:

$ apt-cache policy git
git:
  Installed: 1:2.43.0-1ubuntu7.4
  Candidate: 1:2.43.0-1ubuntu7.4

Installed is what you have. Candidate is the newest version apt knows about. When they're different, an update is waiting. That one comparison is the whole job. Everything else on this page is just doing it on a schedule.

Check

You can see your app's Installed and Candidate versions, and you know that Ubuntu's own timer keeps the Candidate fresh.

Step 2

A script that checks once

Always make it work by hand before you put it on a timer. Create the folder and the file:

mkdir -p ~/.local/bin
nano ~/.local/bin/update-check.sh

Paste this in, then Ctrl + O to save and Ctrl + X to leave:

#!/usr/bin/env bash
# update-check.sh: say whether a newer version of one package is waiting.
# It never installs anything. Usage: update-check.sh <package>
pkg="${1:?usage: update-check.sh <package>}"
log="$HOME/.local/state/update-check.log"
mkdir -p "$(dirname "$log")"

installed=$(dpkg-query -W -f='${Version}' "$pkg" 2>/dev/null)
if [ -z "$installed" ]; then
  echo "$(date '+%F %T') $pkg is not installed" >> "$log"
  exit 0
fi
candidate=$(apt-cache policy "$pkg" | awk '/Candidate:/ {print $2}')

if [ "$candidate" != "(none)" ] && dpkg --compare-versions "$candidate" gt "$installed"; then
  msg="$pkg $candidate is waiting (you have $installed)"
  notify-send "Update waiting" "$msg" 2>/dev/null || true
else
  msg="$pkg is up to date ($installed)"
fi
echo "$(date '+%F %T') $msg" >> "$log"
echo "$msg"

Make it runnable, then run it:

$ chmod +x ~/.local/bin/update-check.sh
$ ~/.local/bin/update-check.sh git
git is up to date (1:2.43.0-1ubuntu7.4)
What each part does

dpkg-query reads the installed version, and apt-cache policy the candidate. dpkg --compare-versions compares them the way apt does: version numbers aren't ordinary numbers, so 2.10 is newer than 2.9. notify-send pops up the desktop note. Every run also adds one line to a log file, so there's a record even if you weren't at the screen.

Experiment

Run it with a package name you don't have, like update-check.sh no-such-thing. What does it print, and what lands in the log? Look with cat ~/.local/state/update-check.log.

Check

The script prints a sensible line for your app, and the log file has one line per run.

Step 3

Two small files: what to run, and when

systemd, the part of Ubuntu that starts and runs everything, splits a scheduled job into two files. A service says what to run. A timer says when. Your own ones live in your home folder:

mkdir -p ~/.config/systemd/user
nano ~/.config/systemd/user/update-check.service
[Unit]
Description=Check whether an update is waiting (never installs)

[Service]
Type=oneshot
ExecStart=%h/.local/bin/update-check.sh git

%h means your home folder. Type=oneshot means "run it, let it finish, done". Now the timer, with the same name but ending .timer:

nano ~/.config/systemd/user/update-check.timer
[Unit]
Description=Weekly update check, Tuesdays at 21:00

[Timer]
OnCalendar=Tue *-*-* 21:00:00
Persistent=true

[Install]
WantedBy=timers.target

OnCalendar is the schedule: day of the week, then year-month-day (* means any), then the time. Persistent=true is the clever bit: if the computer was off at 9pm on Tuesday, it runs the check the next time it starts up, instead of waiting a whole week.

Check the schedule before you trust it

systemd will tell you exactly when a schedule next fires. This is a read-only check, and it's worth doing every time:

$ systemd-analyze calendar 'Tue *-*-* 21:00:00'
Normalized form: Tue *-*-* 21:00:00
    Next elapse: Tue 2026-11-10 21:00:00 GMT
       From now: 6 days left
Experiment

Try a few schedules before you pick one: 'Mon..Fri 08:30', '*-*-01 09:00', 'daily'. Add --iterations=3 to see the next three times. What does each one mean?

Step 4

Switch it on

systemctl --user daemon-reload                  # re-read your unit files
systemctl --user enable --now update-check.timer
systemctl --user list-timers update-check.timer
NEXT                        LEFT   LAST PASSED UNIT               ACTIVATES
Tue 2026-11-10 21:00:00 GMT 6 days -    -      update-check.timer update-check.service

--user is important: it means your systemd, running as you, not the system-wide one, so no sudo. enable makes it survive a reboot, and --now starts it straight away. LAST shows a dash until it has run once.

Don't wait a week to find out it works

Run the service by hand, right now, exactly as the timer will:

systemctl --user start update-check.service
tail -n 3 ~/.local/state/update-check.log
journalctl --user -u update-check.service -n 5 --no-pager

journalctl shows what the service printed and whether it finished cleanly. If the script has a typo, this is where you'll see it.

Check

list-timers shows your next Tuesday, and a manual start adds a fresh line to the log.

When you won't see the pop-up

The note only appears if you're logged in to the desktop when it runs. If you're not, the check still happens and the log still gets its line. Read it any time with tail ~/.local/state/update-check.log.

Step 5

When it says an update is waiting

That's your cue, not the computer's. Do it the pre-flight way: look first, then decide.

apt-cache policy git                 # look: which version, from where?
sudo apt update
sudo apt install --only-upgrade git  # upgrade just this app, nothing else

--only-upgrade means it will upgrade the app if it's installed, but never install it fresh, and it leaves everything else alone.

Step 6

How to undo it all

Write down how to take something out before you put it in. For this:

systemctl --user disable --now update-check.timer
rm ~/.config/systemd/user/update-check.service ~/.config/systemd/user/update-check.timer
systemctl --user daemon-reload
rm ~/.local/bin/update-check.sh ~/.local/state/update-check.log

Why not use cron, the older way of scheduling things? You can, but a timer gives you list-timers to see what's coming, journalctl to see what happened, and Persistent=true for the evenings the computer was off. For a beginner, being able to see it working is worth a lot.

What I'd want you to take away

By hand first

Make the script work on its own, then the schedule, then switch it on. Three small tests beat one big mystery.

What, then when

A service says what to run. A timer says when. systemd-analyze calendar proves the when before you trust it.

Tell, don't do

Let the machine do the remembering. Keep the decisions, and the changes, for yourself.
