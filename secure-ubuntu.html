Securing Ubuntu

Most security guides hand you a script to paste. You end up with a locked-down machine and no idea what was locked, or why. This one asks six questions of your own computer, and you answer each by looking. Along the way you'll watch a firewall block your own phone, which is the moment it stops being abstract.

Before you start

What you need, and the order it goes in

A computer with Ubuntu freshly installed. Mine is nix6, a 2015 desktop rescued from the scrap pile. I've locked down my Raspberry Pis the same way, and this is the order that works for me.

You'll need to be comfortable opening the terminal and reading the prompt. If you're not yet, Meet the terminal takes twenty minutes and everything here builds on it.

Some commands start with sudo. It means "do this as the administrator", and it will ask for your password, which stays invisible as you type. That's normal.

Two rules

Sit at the machine itself, not controlling it from another computer. Step 4 changes how you log in remotely, and if you get it wrong from a distance you can lock yourself out.

Look before you change. Every question starts with a command that only looks. Change something only once you know what you're changing.

Question 1

Who can use this machine?

Every account is a way in, and accounts with admin rights are the ways in that matter most. On Ubuntu, admin rights come from being in a group called sudo.

Predict first

You set up one account when you installed Ubuntu. How many people do you think have admin rights?

$ getent group sudo   # who is in the admin group?
$ ls /home            # whose home folders exist?

On a machine with one user called iain, the first prints sudo:x:27:iain: the group's name, a placeholder, its number, then its members. The second shows one folder, iain.

What if you find someone you don't recognise?

On a machine you installed yourself, that would be very unusual, so stop and find out before carrying on. On a second-hand machine that wasn't freshly installed, old accounts are common, and a fresh install is the cleanest fix. If someone else genuinely shares the computer, give them an ordinary account without admin rights: Settings → System → Users, and leave "Administrator" switched off.

Check

You know every account on the machine, and only the people who should have admin rights are in the sudo group.

Question 2

What's listening?

Programs that wait for connections are said to listen on a port, a numbered door. One command lists every open door:

$ sudo ss -tulpn

The letters ask for tCP and uDP connections, only listening ones, the program behind each, and numbers rather than names. The output is dense, so paste it into the box below and it'll be explained line by line. Nothing you paste leaves your browser.

Nothing is sent anywhere
The one thing to look at

Look at the address in front of each port number. Some start 127. or [::1]. Others are 0.0.0.0, * or [::]. What do you think the difference is?

The difference

127.0.0.1 (and [::1], its newer twin) means this computer only. Nothing else on your network can knock on that door. 0.0.0.0, * and [::] mean any network this computer is on. Those are the doors that matter, and the ones the next question is about.

Ollama, the local AI model I run on nix6, listens on 127.0.0.1:11434 by default. That's exactly right for it: reachable from the machine itself, and from nowhere else. The example in the box above includes it.

Check

You can say which of your open ports only this computer can reach, and which the network can.

Question 3

Who can reach those doors?

A firewall decides which knocks get answered. Ubuntu comes with one called UFW, the "uncomplicated firewall". It's installed, but switched off.

Predict first

Before you check: is your firewall on?

$ sudo ufw status

On a fresh install it says Status: inactive. Before switching it on, let's make something for it to block, so you can watch it work.

Experiment: open a door, then close it

Python can serve a folder as a tiny website. It listens on every network, so your phone can reach it. Make an empty folder first, so there's nothing private in it to see:

$ mkdir ~/firewall-test && cd ~/firewall-test
$ echo "Hello from my computer" > hello.txt
$ hostname -I           # your address on the network, e.g. 192.168.0.23
$ python3 -m http.server 8000

Leave that running. On your phone, connected to the same Wi-Fi, open the browser and go to your computer's address with :8000 on the end, for example http://192.168.0.23:8000. You'll see hello.txt.

Now open a second terminal window (Ctrl + Alt + T again) and switch the firewall on:

$ sudo ufw enable
$ sudo ufw status verbose
Predict first

Refresh the page on your phone. What happens? And will the page still open on the computer itself, at http://localhost:8000?

What happens

The phone gives up: the page spins, then fails. The computer itself still opens it fine. The firewall only guards the doors from outside. status verbose shows why: Default: deny (incoming), allow (outgoing). Nothing gets in unless you allow it, and everything you start from inside still works.

Stop the little web server with Ctrl + C in the first window. You can delete the test folder with rm -r ~/firewall-test once you're back in your home folder.

Check

Your phone could reach the test page with the firewall off, and couldn't with it on. sudo ufw status now says active, and it stays on after a restart.

Question 4

How would you get in from another computer?

Only if you want to. SSH lets you type into this computer's terminal from another one. Ubuntu Desktop doesn't include it, so if you won't use it, the most secure choice is to leave it off and move on to question 5.

I use it on my Raspberry Pis, which have no screen or keyboard: SSH from my laptop is the only way I talk to them. Here's the safe order:

# on the machine you're securing
$ sudo apt install openssh-server
$ sudo ufw allow ssh      # open exactly one door, port 22

Use a key instead of a password

A password can be guessed. A key is a pair of files: a private half that never leaves your laptop, and a public half you give to the computers you want to log in to. On the other computer, the one you'll connect from:

# on your laptop, not the machine you're securing
$ ssh-keygen -t ed25519            # press Enter to accept the file name, then choose a passphrase
$ ssh-copy-id iain@192.168.0.23    # your username and the address from hostname -I
$ ssh iain@192.168.0.23
Watch the prompt

After that last command, look at your prompt. What changed, and why does it matter?

What changed

On my laptop it goes from iain@nix5:~$ to iain@nix4b:~$, one of my Pis. Same window, same laptop, but every command now runs on the other computer. This is why reading the prompt becomes a habit: two terminal windows can look identical and be on different machines. Type exit to come back.

Then switch passwords off

Once the key works, stop SSH accepting passwords at all. Settings go in a small file of your own, rather than editing Ubuntu's main settings file:

$ sudo nano /etc/ssh/sshd_config.d/10-local.conf

Type these two lines, then save with Ctrl + O, Enter, and leave with Ctrl + X:

PasswordAuthentication no
PermitRootLogin no

Now check what SSH will actually use, rather than trusting what you typed. This asks SSH to print its final settings:

$ sudo sshd -T | grep -i -e passwordauthentication -e permitrootlogin
passwordauthentication no
permitrootlogin no
$ sudo systemctl restart ssh
Keep a way back in

Before you close anything, open a new window on your laptop and log in again with ssh. If it works, you're done. If it doesn't, you still have the machine in front of you to fix it. This is why the first rule was to sit at it.

A small thing that surprised me: SFTP, the secure way to copy files between computers, runs inside SSH, on the same door. When I closed the old FTP port on one of my Raspberry Pis, I lost nothing. SSH already did the job, encrypted.

Check

Either SSH isn't installed, because you don't need it, or you can log in with your key, and sshd -T shows passwordauthentication no.

Question 5

Does it update itself when you're not looking?

Most attacks use holes that were fixed months ago on machines that never got the fix. Ubuntu can install security fixes on its own. The question is whether yours is.

Predict first

Do you think automatic security updates are on by default? Check:

$ cat /etc/apt/apt.conf.d/20auto-upgrades
What it means

You'll see two lines ending in "1". The first means "check for updates every day", and the one mentioning Unattended-Upgrade means "install the security ones automatically". "0" would mean off. On a normal Ubuntu install, both are on.

Don't take the settings file's word for it. Find the evidence that it has actually run. It keeps a diary:

$ less /var/log/unattended-upgrades/unattended-upgrades.log

Press Q to get out, just like a manual page. On a machine installed today the file may not exist yet. Check again in a day or two.

Automatic updates cover security fixes. Everything else is up to you, and it's worth doing weekly:

$ sudo apt update && sudo apt upgrade
Check

The settings file shows "1" twice, and within a few days the log shows it running.

Question 6

If it all went wrong, could you get your files back?

Security isn't only keeping people out. A dead drive, a mistaken rm, or a bad update loses files just as surely. Ubuntu's Backups app copies your home folder to an external drive or a network folder on a schedule. If it isn't installed:

$ sudo apt install deja-dup

Open Backups, choose where to save, and run the first backup. Then do the part almost everyone skips:

Experiment

Make a file called test-restore.txt with a line of text in it, run a backup, then delete the file. Get it back using Restore.

A backup you've never restored from is only a hope. The first time you restore should be a practice, not an emergency.

Check

You deleted a file and got it back from your backup.

Going further

Check from the outside

Everything so far checked the machine from the inside. To see it as a stranger would, knock on every door from another computer. nmap does exactly that. From your laptop:

$ sudo apt install nmap
$ nmap 192.168.0.23

The first time I did this on one of my Raspberry Pis, after locking it down, it reported 999 filtered ports and one open: 22/tcp open ssh. The firewall didn't even answer for the other 999. That one line is the whole of this page, measured.

Only your own machines

Scan computers you own. Scanning other people's without permission can be against the law, and on a work network it's the quickest way to meet the IT department.

Your turn

What would you skip?

You have a Raspberry Pi that only ever sits on your home network, controlled from your laptop. Which of the six questions still matter, and which could you reasonably skip?

My answer

I'd skip none, but the weights change. SSH (4) becomes the most important, because it's the only way in and it's switched on. Keys and the firewall (3) matter even at home, because every other device on your Wi-Fi, including the smart plug, shares that network. Updates (5) still matter. Backups (6) matter more than you'd think, because SD cards wear out. The one I'd spend least time on is 1, because a Pi usually only ever has me on it.

That's it

What I'd want you to take away

Look first, then change

Every question started with a command that only looked. You can't secure a door you haven't noticed.

Check what's actually running

sshd -T, the update log, a real restore. Settings files say what you asked for. Checks say what you got.

Fewer doors is safer

The strongest setting for something you don't use is not installing it at all.
